# 보안 팀 프로젝트 중간보고서: 기초 인프라 구축

작성일: 2026년 11월 12일  
프로젝트: 허니팟 기반 재공격 탐지 기능을 갖춘 웹 취약점 진단 및 대응 시스템 개발

> 중간보고서 작성을 위한 비공식 초안이다. 외부 접속 구간은 일반적인 클라우드 VM의 공인 IP 접근 방식으로 가정하여 서술했다. 공인 IP 할당·보안 그룹 설정·공인망 접속을 실제 수행하거나 검증했다는 의미는 아니다. 컨테이너 구성과 내부 검증 결과는 기존 구축 기록을 근거로 작성했다.

## 1. 구축 목적 및 범위

본 프로젝트는 가상의 성적관리 웹서비스에서 SQL Injection, 저장형 XSS, Path Traversal을 재현하고, 코드 패치와 사고 대응 및 WAF·허니팟의 효과를 검증하는 것을 목표로 한다. 이번 단계에서는 해당 기능을 개발하고 실험할 수 있는 공통 실행 환경을 구축하였다.

구축 범위는 클라우드 VM의 실행 도구 준비, Docker Compose 기반 서비스 구성, 정상 서비스와 허니팟의 통신·데이터 분리, 최소 웹 애플리케이션 배포, 상태 점검 및 기본 로그 검증으로 한정하였다. 실제 취약점과 공격 탐지 규칙은 후속 단계에서 구현한다.

## 2. 개발 및 실행 환경

하나의 Ubuntu VM에서 서비스별 컨테이너를 분리하여 실행하였다. Python 실행 의존성은 컨테이너 내부에 설치하고, 호스트에서는 Docker Engine과 Docker Compose로 서비스의 빌드·기동·상태를 관리하도록 구성하였다.

| 항목 | 구성 |
| --- | --- |
| 운영체제 | Ubuntu 24.04.5 LTS, x86_64 |
| VM 자원 | vCPU 4개, 메모리 약 8GB, 루트 디스크 약 58GiB |
| 컨테이너 실행 | Docker Engine 29.9.3 |
| 서비스 관리 | Docker Compose 5.7.1 |
| 리버스 프록시 | Nginx 1.30.6 |
| 애플리케이션 | Python 3.13.18, Flask 3.1.3 |
| WSGI 서버 | Gunicorn 27.0.0 |
| 데이터 저장 | 앱별 SQLite 3.40.1 및 독립 파일 볼륨 |
| 형상 관리 | Git, GitHub |

동일 환경을 재구성할 수 있도록 Python 의존성 버전과 기반 이미지 digest를 고정하였다. 소스와 설정은 GitHub 저장소로 관리하고, 실행 데이터와 비밀 설정은 소스에서 분리하였다.

## 3. 전체 서비스 구성

서비스는 `nginx`, `gateway`, `web`, `honeypot`의 네 개 컨테이너로 구성하였다.

| 서비스 | 역할 | 실행 상태 및 현재 구현 범위 |
| --- | --- | --- |
| nginx | 웹 요청의 단일 진입점과 내부 요청 전달 | 프록시 설정, 요청 ID 생성, 기본 요청 로그 구성 |
| gateway | 백엔드 전달 및 향후 WAF·허니팟 분기 위치 | 고정된 정상 앱 또는 허니팟으로 전달하는 WSGI 골격 |
| web | 정상 성적관리 서비스의 개발 기반 | Hello World HTML 페이지와 상태 점검 제공 |
| honeypot | 정상 서비스와 분리된 미끼 서비스의 개발 기반 | 독립 앱 식별 응답과 상태 점검 제공 |

보고서에서 가정하는 외부 요청 흐름은 다음과 같다.

```text
팀원 PC의 웹 브라우저
        │
        │ http://<VM_PUBLIC_IP>:8080/
        ▼
클라우드 VM의 웹 진입점
        │
        ▼
Nginx → Gateway → 정상 앱(web)
              └→ 허니팟(honeypot, 고정 실험 설정으로 선택)
```

공인 IP 기반 배포 시에는 클라우드 보안 그룹과 호스트 진입 정책에서 팀원 등 승인된 실습 출발지만 TCP 8080에 접근하도록 제한하는 구성을 전제로 한다. 이 외부 접근 정책은 본 초안의 가정이며 실제 적용 완료 항목에는 포함하지 않는다.

호스트에 게시하는 웹 포트는 Nginx의 8080 하나로 한정하고, gateway·web·honeypot에는 별도의 호스트 포트를 게시하지 않았다. 게이트웨이는 사용자가 지정한 임의의 목적지로 요청을 전달하지 않으며, 정해진 두 백엔드만 사용한다. 현재 기본 전달 대상은 정상 앱이다.

## 4. 네트워크 및 데이터 분리

### 4.1. 네트워크 분리

Docker 네트워크를 요청 진입, 정상 앱, 허니팟 용도로 나누었다.

| 네트워크 | 연결 서비스 | 분리 방식 |
| --- | --- | --- |
| frontnet | nginx, gateway | 웹 진입과 게이트웨이 통신 |
| appnet | gateway, web | internal 및 isolated 모드 적용 |
| honeynet | gateway, honeypot | internal 및 isolated 모드 적용 |

정상 앱과 허니팟은 동일 네트워크에 연결하지 않았다. 두 백엔드 네트워크에 연결된 게이트웨이는 프런트 네트워크 주소에서만 HTTP를 수신하도록 제한하여, 허니팟이 게이트웨이에 재진입해 정상 앱으로 우회하는 경로를 제한하였다.

초기 검사에서는 일반 internal 네트워크에서도 컨테이너가 호스트 브리지 주소의 SSH 포트에 연결할 수 있음을 확인하였다. 이를 보완하기 위해 두 백엔드 네트워크에 isolated 모드를 적용하고, 해당 연결이 실패하는 것을 재확인하였다. 이러한 구성은 검증한 통신 경계를 분리하는 것이며 컨테이너를 완전한 VM 수준으로 격리한다는 의미는 아니다.

### 4.2. 데이터 및 파일 분리

| 볼륨 | 사용 서비스 | 용도 |
| --- | --- | --- |
| web-data | web | 정상 앱의 SQLite DB와 향후 세션 데이터 |
| web-files | web | 정상 앱의 실습용 파일 |
| honeypot-data | honeypot | 허니팟 전용 SQLite DB와 향후 세션 데이터 |
| honeypot-files | honeypot | 허니팟 전용 미끼 파일 |
| gateway-data | gateway | 향후 차단·분기 상태 저장 공간 |

현재 DB에는 서비스 식별용 인프라 메타데이터만 저장하며 계정·성적·세션 기능은 아직 구현하지 않았다. 정상 앱의 데이터·파일 볼륨은 허니팟에 연결하지 않았다. 각 서비스의 데이터 디렉터리와 파일 디렉터리에 동일한 이름의 임시 마커를 저장하여 값이 서로 덮어쓰이지 않음을 확인하고, 앱 재시작 후에도 각 값이 유지됨을 검증하였다. 검사 후 임시 마커는 정리하였다.

## 5. 실행 안정성 및 로그 구성

Flask 앱은 개발용 서버 대신 Gunicorn으로 실행하며, 앱과 게이트웨이는 비루트 사용자로 구동한다. 읽기 전용 루트 파일시스템과 제한된 쓰기 공간을 사용하고, 상태 점검과 의존 서비스의 준비 상태를 기준으로 기동 순서를 구성하였다.

`/healthz`는 서비스 준비 상태를 확인하는 경로다. 앱은 DB 조회와 저장 디렉터리 권한을 확인하고, 게이트웨이는 두 백엔드의 상태를 확인한다. 프로세스 종료 시 재시작하도록 설정했으며, unhealthy 상태만으로 자동 재시작되는 구성은 아니다.

기본 로그에는 시각, 요청 ID, 서비스명, 이벤트 유형, 출발지 IP, HTTP 메서드, 경로, 응답 상태와 처리 결과를 기록한다. Nginx에서 요청 ID를 새로 생성하고 프록시 헤더를 재설정하여 외부에서 임의로 지정한 값을 그대로 신뢰하지 않도록 구성하였다.

로그에는 쿼리·요청 본문·비밀번호·인증 헤더·원본 세션 토큰을 기본 기록하지 않으며, 경로 길이는 제한한다. 서비스별 Docker 로그 회전을 적용하였다. 향후 구현할 관리자 로그 화면과 이벤트 검색 기능은 이번 단계에 포함하지 않았다.

## 6. 기술적 문제 및 해결 방법

### 발생한 오류들

1. **컨테이너 내부 HTTPS 연결 지연**

    Docker 이미지 빌드 과정에서 Python 패키지 다운로드가 시간 초과로 실패하였다. VM 네트워크의 MTU는 1442였지만 Docker 기본 네트워크는 1500으로 설정되어 있었다. 이로 인해 컨테이너가 VM 네트워크의 MTU보다 큰 패킷을 전송하면 패킷 손실이나 재전송으로 HTTPS 연결 지연·시간 초과가 발생할 가능성이 있다.

2. **기본 웹 로그에 불필요한 요청 정보 기록**

    로그 보호 검사 중 Nginx의 기본 접근 로그에 쿼리 문자열의 테스트 값이 기록되는 것을 확인하였다. 별도의 JSON 로그를 추가한 상태에서도 기본 로그가 함께 출력되고 있었다.

    ```text
    검사 요청 예시:
    GET /?password=TEST_SECRET

    기본 접근 로그 예시:
    "GET /?password=TEST_SECRET HTTP/1.1" 200 ...
    ```

    실제 비밀번호나 토큰이 같은 방식으로 전달되면 로그에 남을 수 있는 문제였다.

3. **허니팟에서 호스트 서비스 접근 가능**

    내부 네트워크를 분리했음에도 허니팟 컨테이너에서 호스트 브리지 주소의 SSH 포트로 TCP 연결이 가능하였다. `internal` 설정만으로 호스트 서비스 접근까지 차단되지는 않았다.

### 해결방법 및 접근 방식

1. **MTU 비교 실험을 통한 연결 문제 해결**

    MTU를 1442로 설정한 임시 Docker 네트워크에서 동일한 HTTPS 요청이 성공하는 것을 확인하였다. 이후 Docker 기본 네트워크와 프로젝트 네트워크의 MTU를 VM 환경에 맞추어 패키지 설치와 이미지 빌드를 완료하였다.

2. **로그 설정 단일화 및 민감정보 기록 검사**

    Nginx 기본 접근 로그를 제거하고 요청 ID, 메서드, 경로, 응답 상태 등 필요한 필드만 JSON 형식으로 기록하도록 변경하였다. 가짜 민감값을 쿼리·본문·인증 헤더·쿠키에 넣어 요청한 뒤 해당 값이 로그에 남지 않는 것을 확인하였다.

    ```json
    {
      "request_id": "example-request-id",
      "service": "nginx",
      "method": "GET",
      "path": "/",
      "status": 200
    }
    ```

3. **격리 설정 보완 및 실제 연결 재검증**

    정상 앱과 허니팟의 내부 네트워크에 `isolated` 모드를 적용하여 호스트 브리지 주소를 통한 접근을 제한하였다. 적용 후 허니팟에서 호스트 SSH 포트와 정상 서비스로의 접근이 실패하고, 정상 요청 전달은 유지되는 것을 확인하였다.

    ```yaml
    networks:
      appnet:
        internal: true
        driver_opts:
          com.docker.network.bridge.gateway_mode_ipv4: isolated

      honeynet:
        internal: true
        driver_opts:
          com.docker.network.bridge.gateway_mode_ipv4: isolated
    ```

공인 IP 접속 시나리오에서는 브라우저로 위 주소를 열었을 때 Hello World 페이지와 상태 확인 링크가 표시되는 것을 확인 대상으로 한다. 해당 주소는 설명용 자리표시자이며 실제 공인 IP나 접속 증빙으로 사용하지 않는다.

후속 단계에서는 다음 기능을 순차적으로 구현한다.

1. 역할별 인증과 서버 측 세션, 성적관리·게시판·파일 조회 기능 개발.
2. 취약 버전에서 SQL Injection·저장형 XSS·Path Traversal의 영향 재현.
3. 패치 버전에서 WAF를 비활성화한 상태로 동일 공격 실패와 정상 기능 유지 검증.
4. WAF 규칙과 재공격 판단 조건, 허니팟 전환 및 행위 기록 구현.
5. 세션 폐기·성적 복구·IP 차단과 관리자 분석 화면 개발.
6. 고정 요청 집합으로 탐지율·차단율·오탐률 측정 및 보고서 정리.

추가 운영 검증으로는 VM 재부팅 후 동작, 백업·복원, 다른 VM으로의 이전이 남아 있다. Compose 파일은 서비스 구성을 재현하지만 새 VM의 실행 도구·호스트 설정·네트워크 준비와 데이터 볼륨 복원까지 자동으로 수행하지는 않는다.
